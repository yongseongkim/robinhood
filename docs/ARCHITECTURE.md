# 시스템 구조와 처리 기준

실행 절차는 [설치 안내](INSTALL.md), 운영 권한과 서비스 활성화는 [배포 안내](../deploy/README.md), 수집 시점별 건수는 [데이터 출처 기록](DATA_SOURCES.md)에서 확인합니다.
이 문서는 공개자료가 조회 데이터가 되는 과정과 집계 기준을 설명합니다.

`robinhood-server`는 수집 worker와 FastAPI 조회 API를 실행하고, `robinhood-web`은 API 응답을 React·TypeScript 화면에 표시합니다.
운영 데이터는 메인 PostgreSQL의 `robinhood` 스키마에 저장합니다.
PostgreSQL 연결 URL이 없으면 로컬 SQLite를 사용합니다.
`site/`는 별도로 배포할 수 있는 정적 사이트입니다.

```text
Public sources -> Worker -> raw -> staging -> normalized + findings
                                                  |
                                                  v
                                            validate index
                                                  |
                                                  v
                                             PostgreSQL
                                                  |
                                                  v
                                            FastAPI -> React

Worker <-> PostgreSQL (job_runs / job_schedule / ocr_corrections)
normalized + findings -> legacy build (optional) -> site/data
```

서버 worker도 지도 경계와 인접 정보를 만들기 위해 `build_geo.py`를 실행합니다.
마지막 단계인 `build_site.py`는 정적 사이트 데이터를 배포할 때만 실행합니다.

PostgreSQL에 발행하기 전에 정규화한 자료로 임시 SQLite 인덱스를 만들고 검증합니다.
사용을 마친 임시 인덱스는 삭제합니다.
주체·거래처·문서·거래·탐지 결과는 관계형 테이블에, 재산·법안·재정·지도·출처 정보는 JSONB에 저장합니다.
운영 API는 PostgreSQL 연결에 실패하면 조회 오류를 반환합니다.
원본 PDF·XLSX와 OCR 파일은 현재 디스크에 보관하며, 향후 객체 저장소로 옮길 수 있습니다.

발행할 때는 하나의 트랜잭션에서 이전 조회 자료를 `DELETE`하고 새 자료를 `COPY`한 뒤 무결성을 검사합니다.
어느 단계든 실패하면 전체를 롤백합니다.
조회 요청은 `REPEATABLE READ READ ONLY` 트랜잭션을 열기 때문에 발행 도중에도 한 응답 안에 서로 다른 버전의 자료가 섞이지 않습니다.
수집과 발행은 같은 세션 advisory lock을 사용합니다.
발행은 잠금을 획득한 연결에서만 할 수 있으므로 연결이 끊어지면 그 작업의 발행도 실패합니다.
원본 캐시와 DB는 별도로 백업합니다.

운영 worker는 PostgreSQL의 `job_schedule`에서 다음 실행 시각을 확인하고, 작업 후 30초 간격으로 다시 확인합니다.
기본 설정에서는 성공한 시각에서 24시간 뒤에 다음 수집을 시작합니다.
실패하면 1분, 5분, 15분 뒤에 차례로 재시도한 뒤 정규 주기로 돌아갑니다.
재시작해도 저장한 일정을 사용합니다.
외부 CronJob에서도 `run-due`로 같은 일정을 확인할 수 있습니다.
실행 이력은 `job_runs`에 저장합니다.
API는 작업 상태와 이력 조회를 제공하며, 수집 시작과 systemd 서비스 활성화는 운영 환경에서 수행합니다.

개발 환경에서는 Vite가 `/api` 요청을 FastAPI로 전달합니다.
운영 환경에서는 FastAPI가 빌드한 정적 파일을 제공하고 화면 경로 요청에는 `index.html`을 반환합니다.
응답의 `scope`에는 재원과 조회 기간, 보고분·월·연간·기준일 등 집계 기준을 표시합니다.
금액은 재원별로 집계하고 결측값은 `null`로 둡니다.
인물과 상호는 원자료의 이름으로 표시하고 개인 수령인과 개인사업자 번호는 가립니다.
네이버 지도는 공개 키 ID로 불러오며, 구별 대표 좌표에 거래처 수를 표시합니다.
개별 가게 좌표 수집, Geocoding, Toss 플랫폼 연동은 구현 범위 밖입니다.

자료마다 지원 연도와 첨부 캐시, 인증키, OCR에 필요한 환경이 다릅니다.
출처별 수집 시각과 대상 기간을 확인하는 방법은 [서버 안내](../robinhood-server/README.md)에 있습니다.

## OCR 정정 계층

선택적 정정 단계에서 worker는 `parse_ocr.py`가 추출한 표 텍스트를 Codex에 보냅니다.
PDF·이미지·원문 URL·파일 경로는 모델 입력에서 제외합니다.
원본 파일은 서버에서 해시를 확인하고 `data/raw/`의 원본과 OCR 추출 JSONL은 보존합니다.

`ocr_corrections`에는 `doc_id`, 원본과 추출 행의 해시, 프롬프트·모델 설정, 추출 행 사본, 정정 전후 문구와 근거·검증 결과를 기록합니다.
조회 테이블을 다시 발행해도 정정 이력은 유지합니다.
worker가 검증된 정정본을 `var/ocr-corrections.json`으로 내보내면 정규화 단계에서 추출 행의 해시가 일치할 때만 적용합니다.
수치·기간·주체·재원·행 수는 보존하며 중복 거래는 정정 전 문구로 판별합니다.
거래 상세에는 정정 적용 여부와 추출 당시의 OCR 신뢰도를 표시합니다.

SDK를 쓰려면 배포 환경에 ChatGPT 로그인을 설정해야 합니다.
API 키로 인증한 경우 정정 호출을 중단합니다.
실행당 묶음 수와 묶음당 행 수·입력 길이, 호출 시간을 제한합니다.
`ROBINHOOD_OCR_CORRECTION_ENABLED`를 켜면 새 검토를 요청할 수 있습니다.
꺼 둬도 입력과 설정이 같은 검증 완료 정정본은 재사용합니다.
로그인과 운영 DB 연결, 상시 실행 여부는 배포 환경에서 설정합니다.

```
raw -> staging -> normalized -> findings -> validate / publish
normalized + findings -> legacy site/data (optional)
```

|---|---|---|
| 수집 | `collect_ka_money.py`, `collect_gwanak.py`, `collect_mapo.py`, `collect_seoul.py`, `districts/g*.py collect`, `collect_roles*.py` | `data/raw/<source>/` + `manifest.json` (URL, sha256, 수집 시각). 이미 받은 파일은 건너뜀 |
| 수집 (API) | `collect_assembly.py`, `collect_votes.py` (열린국회정보), `collect_fiscal.py` (열린재정) | `data/raw/assembly/`, `data/raw/assembly/votes/<대수>/<BILL_ID>.json`, `data/raw/fiscal/<서비스>/` |
| 파싱 | `parse_gwanak.py` (XLSX, 헤더 이름 매핑), `parse_mapo.py`·`parse_seoul.py` (PDF 표 추출), `districts/g*.py parse`, `parse_ocr.py` (스캔본) | `data/staging/<source>.jsonl` + `_parse_report.json` (파일별 행 수·합계·실패 사유) |
| 정규화 | `normalize.py`, `assembly.py`, `collect_fiscal.py`(정리 단계) | `expenditures.jsonl`, `subjects.json`, `merchants.json`, `documents.json`, `funding_types.json`, `assembly.json`, `fiscal.json` |
| 탐지 | `detect.py` + `rules.py` | `findings.json`, `reversal_pairs.json` |
| 사이트 | `build_site.py` (+ `build_rank.py`) | `site/data/meta.js`, `s/<주체>.js`, `m/<버킷>.js`, `money.js`, `rank.js`, `fiscal.js`, 검색 인덱스 (`geo.js`는 `build_geo.py`) |

## 문제별 처리

- 관악구의회 엑셀에서 확인한 서식은 6종입니다.
  파서는 `연번`이 있는 머리글과 바로 아래 `일자/시간/상호명/주소` 등의 보조 머리글을 조합해 열을 찾습니다.
  열을 찾지 못한 파일은 파싱 보고서에 남깁니다.
- 마포구의회 텍스트 PDF에서는 표를 직접 추출합니다.
  병합 셀과 줄바꿈을 복원하고 행별 신뢰도를 `parse_confidence`에 기록합니다.
- 스캔 PDF는 `ocr.py`가 페이지를 300 dpi로 렌더링한 뒤 macOS에서는 Vision, Linux에서는 Tesseract로 글자와 위치를 읽어 `data/ocr/`에 캐시합니다.
  두 엔진 모두 한국어와 영어를 읽습니다.
  Vision은 정확도 우선 모드를 사용하고 언어 보정은 끕니다.
  `parse_ocr.py`는 머리글 위치로 열을 찾으며 띄어쓰기 차이와 한 글자 오독을 허용합니다.
  날짜·시간·금액·결제수단은 값의 형식으로 먼저 판별하고, 한 상자에 붙어 읽힌 칸은 글자 위치로 나눕니다.
  한 자리 인원은 빠지기 쉬워 인원 열이나 해당 칸을 확대해 다시 읽습니다.
  금액과 시각 또는 상호가 있는 행에서 날짜 칸만 비었으면 직전 거래의 날짜를 이어받고 신뢰도를 낮춥니다.
  인쇄된 합계가 있으면 읽은 금액 합계와 대조해 파일별 결과를 남깁니다.
  사용자 칸에서 직책을 고르는 조건은 [OCR 파서의 `sanitize_role`](../pipeline/parse_ocr.py)에서 확인할 수 있습니다.
- KA-money의 OCR 자료는 원본을 보존하고 `ocr: true`로 표시합니다.
  대표 상호가 같고 사업자번호가 한 자리만 다르면 더 자주 나온 번호로 묶습니다(수집본에서 116개).
  상호가 해당 번호의 대표 상호와 일치하지 않고 유사도 조건도 충족하지 않으면 번호를 버리고 `BIZNO_NAME_CONFLICT`를 기록합니다.
- 같은 업체라도 법인 표기·공백·괄호·전각 문자 때문에 상호가 다르게 적힐 수 있습니다.
  NFKC 정규화와 상호키를 이용해 사업자번호, 상호키와 지역, 상호키 순으로 거래처를 식별합니다.
  상호키만 일치하면 신뢰도는 ‘낮음’입니다.
  주소가 없는 거래라도 같은 출처에서 그 상호가 한 시·군·구에만 나타나면 해당 지역 거래처에 연결합니다.
  서울시의회의 ‘서울시청매점’이 그 예입니다.
- KA-money 안에서는 의원번호로 동명이인을 구분합니다.
  열린국회정보 명부·표결과 연결할 때의 조건은 [데이터 출처 문서](DATA_SOURCES.md)에 있습니다.
- 정당과 지역구는 회계보고별로 보관합니다.
  보고 기간 중에 바뀐 날짜는 회계자료만으로 알 수 없습니다.
- 지방의회에서는 같은 직책도 대수와 전·후반기별로 지출 주체를 나눕니다.
  직책 보유자가 바뀌는 기간을 한 사람의 지출로 합산하지 않기 위해서입니다.
- `collect_roles.py`는 의회연혁·역대 의장단·의원 약력 등 공식 홈페이지의 선출 기록에서 직책 보유자를 확인해 `data/staging/role_holders.json`에 저장합니다.
  근거가 된 원문은 `data/raw/roles/`에 보관합니다.
  선출일 이전처럼 보유자를 확인할 수 없는 기간은 ‘미확인’으로 남깁니다.
  사람별 페이지에는 맡았던 직책을 모아 표시하고 경비는 각 직책에 귀속합니다.
- 같은 거래가 반복되면 B4 규칙으로 표시합니다.
  정치자금은 영수증 번호를, 지방의회 경비는 문서 ID를 함께 확인해 실제 반복 거래와 다른 파일에 다시 실린 거래를 구분합니다.
  같은 첨부를 여러 게시글에 올린 경우 최초 게시글에 귀속하고 공개자료 점검 규칙 E1으로 표시합니다.
- 취소·환급 금액은 음수로 기록합니다.
  반환일 180일 전부터 7일 후까지 주체·거래처가 같고 금액의 절댓값이 일치하는 양수 거래를 찾아 연결합니다.
  순지출에는 음수 금액을 반영하며, 원거래를 찾지 못한 반환은 정산성 반환 등의 예외를 제외하고 B5로 표시합니다.
  수입으로만 보고한 반환은 KA-money 지출 내역에서 확인할 수 없습니다.
- 수집기는 원문의 SHA-256 해시를 기록합니다.
  수정·삭제 여부를 다시 확인하는 범위는 [출처별 캐시 정책](../robinhood-server/README.md#실제-자동-갱신-범위)에 따릅니다.
  탐지 결과는 정규화 자료로 다시 계산할 수 있으며, 같은 규칙·주체·근거 거래에는 같은 탐지 ID를 부여합니다.
- 인원이 없으면 1인당 금액을 계산할 수 없고, 시각이 없으면 심야 사용 여부를 판단할 수 없습니다.
  통계 비교는 각 규칙이 정한 최소 표본 수를 충족할 때만 수행합니다.
- 사업자번호 칸에 생년월일이 적혔거나 인건비로 분류된 경우 사용처를 가립니다.
  자유 기재란의 전화번호·이메일과 개인사업자 번호의 뒷자리를 가리고, 거래처 주소는 시·군·구까지만 남깁니다.
  참석자 명단은 파싱하지 않고 정치자금 수입은 유형별 합계만 공개합니다.

## 지역(지도)과 의회 레지스트리

- `pipeline/councils.py`는 기본 의회 3곳의 정보와 구의회 수집기가 `data/staging/councils/<slug>.json`에 기록한 정보를 합칩니다.
  이 목록에서 의회의 표시 이름, 대수 계산의 기준(`term_base_2018`), 관할 지역을 확인합니다.
- ‘근무지와 경계를 접한 시·군·구까지’라는 기준을 적용할 때는 선으로 맞닿은 지역(`adjacent`)과 한 점에서 만나는 지역(`touches`)을 모두 포함합니다.
  관악구와 영등포구처럼 한 점만 접한 경우에도 관할 밖 사용으로 잘못 표시할 가능성을 줄이기 위해서입니다.
- KA-money의 지역명과 오마이뉴스 선거구 경계의 이름을 대조했을 때 제22대 지역구 254곳이 모두 일치했습니다.
  제21대에서 선거구가 바뀐 의원은 해당 회계자료의 지역명만으로 당시 선거구를 특정할 수 없는 경우가 있습니다.
- 제21대 현직 여부는 현직 의원만 수록한 2023년 파일로 확인합니다.
  2024년 상반기 파일에만 있는 109명의 회계는 제22대 총선 예비후보 기간으로 구분했습니다.

## 기존 정적 사이트의 화면별 계산

아래 기준은 `site/`에서 제공하는 정적 사이트에 적용합니다.
React 웹의 필터와 집계는 [repository.py](../robinhood-server/src/robinhood_server/repository.py), [services.py](../robinhood-server/src/robinhood_server/services.py), [scopes.py](../robinhood-server/src/robinhood_server/scopes.py)와 각 화면의 코드를 확인합니다.

- ‘정치인의 돈’(`money.js`)은 후원회 기부금·선거비용 보전·기탁금 반환 등 유형별로 정치자금 수입을 집계합니다.
  계좌 간 이체·이월 누계처럼 중복될 수 있는 항목은 합계에서 빼고 따로 표시합니다.
  지출은 정치자금 회계보고의 대분류 또는 지방의회 `council_category`의 식사·카페·경조사·성금·물품 등 항목으로 나누고, 재원별로 합산합니다.
- ‘많이 쓴 곳’의 B6 규칙은 국회의원 정치자금을 같은 연도·대분류 안에서 비교합니다.
  양의 지출 합계가 있는 의원이 50명 이상일 때, 지출액이 95백분위수 이상이고 중앙값의 3배 이상이며 1천만 원 이상일 때 표시합니다.
  구의회는 6개월 이상 자료가 있는 직책의 월평균 지출을 계산합니다.
  같은 연도·직책에서 월평균이 양수인 비교 대상이 15개 이상이면, 95백분위수 이상이면서 중앙값의 2배 이상인 직책을 표시합니다.
  예산 규모가 다른 서울시의회는 구의회 비교에서 제외합니다.
  점그래프에는 비교 대상 전체를 표시합니다.
- ‘나라 살림’(`fiscal.js`)은 본예산·국회 확정 예산과 12월 누계 결산을 구분합니다.
  부처별 총지출을 펼치면 최근 회계연도의 세부사업 상위 항목을 볼 수 있으며, 다음 연도 정부안이 있으면 별도로 표시합니다.
- 순위판(`rank.js`, `build_rank.py`)은 같은 재원·기간 안에서 금액·건수·비율을 비교합니다.
  국회의원은 제21·22대 의원의 정치자금을 연도별로 비교하고 식사비 평균·비율 순위에는 식사 20건 이상인 주체만 포함합니다.
  지방의회는 직책과 기수별로 의회운영업무추진비를 집계합니다.
  선출 기록이 있는 관악·마포구의회와 서울시의회에서는 직책 보유자별 집계도 제공합니다.
  월평균을 구할 때는 공개 기간에 속하는 날짜만 개월 수 계산에 사용합니다.
  장소 순위에는 사업자 거래처 중 전국 체인·결제대행·배달앱을 제외합니다.
  식대로 분류한 거래라도 상호가 광고·여행사 등에 해당하면 식당 집계에서 제외합니다(`common.CHAIN_STORE`, `NOT_FOOD_PLACE`).
- 재산은 `parse_assets.py`가 국회공보 PDF 표를 pdfplumber로 읽어 `assets.json`에 기록하고, `build_assets.py`가 정적 사이트에 쓸 `assets.js`용 자료를 만듭니다.
  한 페이지의 소속·직위·성명 머리글과 표 행은 위에서 아래로 읽어 각 항목을 신고자에게 연결합니다.
  다음 페이지에 관계·금액이 반복되고 명세만 이어지면 새 주소로 시작하지 않을 때만 앞 행에 붙입니다.
  신고자별로 항목 합계와 구분별 소계를 대조하고, 자산 소계 합에서 채무를 뺀 값이 공보의 총계와 같은지 확인합니다.
  건물에 신고한 전세·임차권은 소유 부동산과 따로 셉니다.
  재산을 정치자금 회계와 연결할 때는 제22대 같은 이름의 주체가 한 명이어야 합니다.
- 가격 차이는 같은 식당에서 인원을 확인할 수 있는 결제들의 1인당 금액 중앙값을 기준으로 계산합니다.
  비교할 결제도 중앙값 계산에 포함합니다.
  식사 결제가 8건 이상이고 중앙값이 8천 원 이상인 식당에서, 1인당 금액이 중앙값의 2배 이상이고 차액이 1만 5천 원 이상인 결제를 표시합니다.
  구내식당·매점·도시락 등과 OCR로 읽은 행은 제외합니다.
  이 값은 해당 식당의 결제 기록 안에서 비교한 결과입니다.
  물품 구매는 수량이 거의 없어 단가를 비교할 수 없습니다.
  나라장터 물품 가격을 시중가와 비교하려면 품목·단가 API와 별도 인증키가 필요한 시중가 자료가 있어야 합니다.
- 의정활동 화면은 대표발의 법률안을 가결·대안 반영·임기만료 폐기·철회·부결·심사 중 등 처리 결과별로 묶습니다.
  표결 참여율은 찬성·반대·기권 건수의 합을 전체 표결 기록 수로 나눠 계산합니다.
  반대·기권 목록에는 해당 표결 전체를, 최근 표결 목록에는 결과와 관계없이 최신 20건을 싣습니다.

## 미구현·후속 작업

1. KA-money 탐지 결과 중 무작위로 고른 100건을 원본 PDF와 대조해 규칙별 오탐률을 `data/reviews.json`에 기록할 예정입니다.
2. 수집 확장 후보는 2012~2022년 KA-money 회계보고, 경기·부산·인천 광역의회 경비, 지방의회 공무국외출장 보고서입니다.
   KA-money 연도별 열 이름 차이는 `KA_COLUMNS`에서 대응합니다.
   지방의원 성명·선거구를 연결하려면 선관위 당선인 API와 공공데이터포털 인증키를, 지방재정을 수집하려면 지방재정365의 별도 API를 검토해야 합니다. [확장 후보 조사 기록](expansion-candidates.json)
3. 나라장터 계약정보 API의 서비스키를 확보하면 기관 단위 계약에 D1~D3 규칙을 적용할 수 있습니다.
   계약은 모델과 화면 모두에서 개인 지출과 분리할 계획입니다.
4. 감사원·권익위 공개 결과는 사람이 검증한 뒤 `AuditFinding`으로 연결하고 통계 탐지 결과와 구분해 ‘확정 사실’로 표시할 계획입니다.
5. 운영 주체가 정해지면 정정 요청을 받을 이메일이나 저장소 이슈 주소를 사이트에 공개할 예정입니다.
